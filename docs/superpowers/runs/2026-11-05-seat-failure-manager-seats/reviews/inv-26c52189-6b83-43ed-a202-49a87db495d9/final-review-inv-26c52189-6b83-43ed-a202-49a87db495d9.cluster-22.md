## Trace against the requirement baseline

- B4 (named non-transient integrity error, distinct from the transient case): the writer is where that difference becomes real behaviour. Before this change, a `MutationError::Store(StoreError::Integrity)` returned from `mutation.apply` (apply_phase, `Ok(Err(MutationError::Store(e))) => return Err(e.into())`) became `Fail::Infra`. `step_inner` then requeued the op to `admitted` and `step` counted it toward `infra_failures`, so the op was retried until the poison cap and the writer looked unhealthy. With the change, the same path reaches `Err(Fail::Data(msg))` in `step_inner`. `finish_failed` then records the op as failed for good, emits `OpState::Failed` and returns `StepOutcome::Failed`, and the FIFO moves on. Production entry point: the daemon writer loop calls `WriterCore::step` for every admitted op. This is the same route `Corrupt` already takes, and `corrupt_data_fails_only_that_op` covers that route end to end. This cluster delivers the writer leg of B4. The other legs (where `Integrity` is produced, the exit code 6 mapping in cli::daemon_error) are outside this cluster and belong to the seam reviewer.
- B6 and B13 (reparenting): when a reparent target or manager chain cannot be resolved inside a planned mutation, the error now fails that one op cleanly instead of retrying it forever. The observed-cascade fallback in hg-k4l.15 (never abort the cascade) is handled inside plan::managers, before any error reaches the writer, and is the seam reviewer's to trace.
- Other baseline rows do not touch this cluster.

## Correctness notes

- `Integrity` is built only from reads of a committed revision (`unresolved` doc: "does not resolve at the committed revision"). Retrying against the same head cannot succeed, so treating it as terminal is correct. If a concurrent commit changes the result, that surfaces through `recheck_relied_on` (which runs earlier) as a rejection or replan, not through `Integrity`.
- The `step` comment ("A stray `Data` (not produced inside the apply phase) counts as infrastructure") still holds. The only store reads outside `apply_phase` are in `finish_commit`, after the ref has moved, and those do not produce `Integrity`.
- The failure reason is written as `corrupt data: {msg}`, so an integrity failure is stored as `corrupt data: st_a: manager st_b not found at the committed revision`. The integrity message is kept in full and the error is still distinct from the transient case. Only the prefix is slightly misleading. This is cosmetic.
