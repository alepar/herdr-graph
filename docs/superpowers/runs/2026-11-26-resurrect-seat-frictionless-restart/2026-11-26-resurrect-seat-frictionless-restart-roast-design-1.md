- [Should-fix] §4.1 "Keyless relaunches wait for `rebind` done in the same incarnation"; §4.2; §4.5 — §4.1 makes the keyless relaunch wait for the rebind, but only a definitive refusal releases it. When the rebind errors, times out or cannot run (threads unreachable), the spec never says the relaunch proceeds, so keyless agents can stay unlaunched indefinitely.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: §4.2 releases the gate only for `NotFound`-as-done and "any other definitive refusal records the refusal, and the relaunch proceeds anyway".
  §4.5 names "could not run (old daemon, threads unreachable)" only to raise a `clones.restart_held` status row after 90 s; it does not release the relaunch.
  All three seats searched the spec for grace, retry, timeout, errored, unreachable and proceed, and found no release for this case.
  The §4 "Today" column has keyless seats relaunching with no threads dependency, so a threads outage at restart time is a regression against B2.
  Bead hg-lnw.5 adds retry-until-grace, but it is outside the spec text and does not say the relaunch then proceeds.
  fix-shape hint: add one sentence to §4.2: an errored, timed-out or unreachable rebind is retried until the 90 s grace, then treated as a refusal, and the relaunch proceeds.
- [Should-fix] §4 opening paragraph ("whose fact, read after the change, is `Unresolved` … A seat already resolved onto its pane needs nothing"); §4.1 — The rebind is emitted only when the post-restart fact reads `Unresolved`. If threads lags and the read is still `Resolved`, no rebind is emitted, and the spec says neither whether the keyless relaunch wait ends nor whether a later `Unresolved` fact re-triggers the rebind.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (refute voted REJECT, outvoted 2 to 1) / ground ✓)
  evidence: §4.2 counts `NotFound` as done only for an emitted rebind, and §4.5 covers only a rebind that was refused or could not run; neither covers a rebind that was never emitted.
  The ground seat searched the spec for lag, caught up, re-plan, stale and ordering, and found nothing.
  The lag is modelled in the repo: src/threads/effects.rs:546 guards a read taken before threads has caught up with a close, and src/observe/tests.rs:3167 has "Threads has not caught up: the fact stays Resolved on the old pane".
  Refute seat dissent: the trigger is a state predicate and the op key is per incarnation, so a level-triggered planner emits the rebind once the fact turns `Unresolved`. Both confirming seats address this: the spec does not state the planner's tick semantics or whether "needs nothing" counts as done for the §4.1 gate.
  fix-shape hint: state the §4.1 gate semantics: what counts as done when no rebind was emitted, and that the rebind is re-planned when the fact turns `Unresolved` later in the same incarnation; consider a caught-up guard like the one for closes.
- [Should-fix] §3 window "from 24 h to 7 d": "Graph's channel wants re-issue graph's own invitations if needed." — The 24 h to 7 d window relies on graph's channel wants re-issuing graph's own invitations "if needed", but no mechanism is specified. Graph's current poll would read the settled invitation as still Pending and satisfied, and never re-invite.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/threads/effects.rs ~L731-738 treats an invitation as satisfied when it is on the recorded seat and `Pending | Accepted`; a resurrect keeps the seat id.
  src/threads/effects.rs ~L2260-2263 maps a missing membership detail to `InvitationState::Pending` ("No membership yet: the invitation is still pending"); src/threads/adapter.rs `detail_of` maps `VoluntaryMembershipState::Absent` to `None`.
  herdr-threads v3.5.0 src/store/seats/reversible.rs `settle_expired`: "UPDATE invitations SET state='recipient_retired',retired_at=?1 WHERE id=?2 AND state='pending'", with requirement-episode invitations excluded (https://raw.githubusercontent.com/alepar/herdr-threads/v3.5.0/src/store/seats/reversible.rs).
  Scope: only ordinary seat-wide invitations still unaccepted at the 24 h settle are affected; Required invitations and accepted memberships return.
  The spec names no change to this mapping and no §6 test row; bead hg-lnw.4 tests the re-issue but names no mechanism.
  fix-shape hint: name the mechanism in §3 (for example, a resurrect past 24 h invalidates recorded Pending ordinary invitation rows, or the poll reads invitation state instead of membership), say which invitations "graph's own" means, and add a tier-5 test row.
- [Nit] §3 table row "keyless, `Retired{Reversible}`"; compare §4.2 — §3 defines no outcome mapping for a refused or failed `resurrect_seat` (`NotFound` after the seat finalized between the fact read and the call, or any other refusal), so the undo can stall on `threads_done` instead of falling through to fresh-seat succession.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (refute voted REJECT, outvoted 2 to 1) / ground ✓)
  evidence: §3 states only the success path ("then `SeatTransition::Acknowledge`"); §4.2 maps `NotFound` and other refusals for the rebind only.
  The ground seat searched the spec for refusal, NotFound, Rejected, defer and retry, and found no mapping for a resurrect refusal.
  The existing `unretire_seat` executor (src/threads/effects.rs ~1546) records the refusal and returns `Deferred` with no fallback.
  Refute seat dissent: the fact is re-read each pass, so a `NotFound` from the Reversible to Final race defers and the next read picks succession. Both confirming seats accept this for the race; the open case is a persistent refusal (`InstanceMismatch`, `Unsupported`, `StaleHostObservation`), which waits until the 7 d fallback.
  severity: seats split Should-fix (reproduce) and Nit (ground). demoted: profile is a single-operator local tool with no external users, the race self-heals on the next fact read, and a persistent refusal behaves as the accepted unretire path does today, so a missing refusal sentence is a Nit here.
  fix-shape hint: add one sentence to §3: a resurrect refusal is recorded and deferred, and the fact re-read picks succession once the seat is Final; say what a persistent non-`NotFound` refusal does.

## Not verified (beyond panel cap)   ← severe candidates the panel cap left unverified — listed, never dropped
- [suggested Should-fix] §3 op key `resurrect:<clone>:<epoch>`; §4 rebind trigger — A Herdr restart during an in-flight undo is unspecified: the resurrect op key resurrect:<clone>:<epoch> carries neither target pane nor incarnation, the seat is Retired not Unresolved so no rebind is emitted, and nothing says how the want is re-targeted or re-keyed.
- [suggested Should-fix] §4 intro; §4 table keyless rows; §4.1 — The spec does not say what triggers the keyless relaunch once the rebind has succeeded. The rebind is emitted only for a fact that reads `Unresolved`, and a successful rebind makes the seat resolved on its pane, so the trigger for the "then resumes" step is undefined.
- [suggested Should-fix] §4 table row "agent never observed, keyless"; §4.1; §4.3 — The §4 row "agent never observed, keyless (`adopt --harness`, no agent) → rebind, then fresh start" is not wired by any rule the spec states. §4.1 gates only relaunches, and §4.3's `launched:` change does not cover a seat graph never launched.
- [suggested Should-fix] §4 table rows "created (keyed) ... rebind also runs; relaunch does not wait on it"; §4.1; §4.2 — Keyed seats get a rebind running concurrently with their key check-in with no ordering; the spec covers only the key-wins-first order and assumes U2 makes the other order harmless.
- [suggested Should-fix] §4 table rows "created (keyed) ... rebind also runs"; B4 — §4 applies the U2 rebind to keyed seats ("rebind also runs"), but U2 as the user asked for it (B4) and as §"Key decisions" describes it is a rebind of a restart-held *keyless* seat. If 3.6.0 refuses keyed seats, every ordinary restart would record `rebind_refused` for every keyed clone.
- [suggested Should-fix] §3 resurrect onto the reopened pane; §4 rebind emission; §4.2 — §3 and §4 assume the service resurrect and rebind succeed as soon as graph asks. The 3.5.0 path needs a fresh threads observation of the target, so a call made before threads has observed the reopened or restarted pane fails with `StaleHostObservation`. The spec does not say whether that error is retryable or definitive.
- [suggested Should-fix] §3 "read from `continuity_key` in `SeatInspect`"; §2 — The keyed/keyless split is read from threads' continuity_key although graph already records keylessness on the clone; the two can disagree (released key, restored store) and the spec does not say which source wins or which undo path such a seat takes.
- [suggested Should-fix] §3 `replace` paragraph — §3 has graph pass `replace` for a bare seat already minted on the reopened pane. Threads refuses a service `replace` when that seat has any membership, or when it holds a key owned by another service, and the spec does not say what graph does after that refusal.
- [suggested Should-fix] §3 "Windows, derived from the seat's `retired_at`"; undo preview — The undo preview's window label is computed from retired_at against graph's clock and fixed durations, while threads settles and finalizes on its own clocks and passes, so the preview can name a different window from the one that applies at execution, with no re-check or tolerance.
- [suggested Should-fix] §4.3; §4 rows "agent never observed, keyed/keyless" — Counting a launched: meta as having had an agent relaunches, after every restart, agents that failed at launch or were deliberately stopped before the restart, with no rule to tell those cases apart and no bound.
- [suggested Should-fix] §4.4 — §4.4's fix (based on a suspected cause) re-applies the ordinary restart rule after the restore launch without bounding relaunches when the restored agent exits immediately, and does not name the follow-up argv.
- [suggested Should-fix] §4 "whose bound pane exists" — The spec never says where the "bound pane" of an `Unresolved` seat comes from after a restart. Graph's own location rule leaves a seated clone whose seat is Unresolved as Unknown, so "whose bound pane exists" has no defined source.
- [suggested Should-fix] §3 table ("Seat fact on the Restore seat | Action") — The §3 table has no action for a Restore seat whose fact is not Retired at undo time: still Resolved because threads has not processed the close yet, Unresolved, or unknown because threads is unreachable.
- [suggested Should-fix] §3 keyless reversible row; §2 `service_session_v4` with `ResurrectSeat` — ResurrectSeat (and presumably U2) runs through the operator repair path, which needs an operator owner uid and attached host on the daemon; a 3.6.0 daemon without them answers Unsupported, and the spec maps no such failure or remedy.
- [suggested Should-fix] §1 gate bead "herdr-threads 3.6.0 tagged with ht-lzhi and ht-0f0r"; Key decisions — The single gate requires both U1 and U2 in one tag, so a slip or reshape of U2 also blocks resurrect-on-undo, which needs only U1; no partial-gate path is described.
- [suggested Should-fix] §2; §3; Main challenges — No migration is specified for undos already in flight or stuck before the upgrade (refused or journalled UnretireSeat effects for keyless seats).
- [suggested Should-fix] §4 `ThreadsPort::rebind_held_seat(seat, pane, op)` versus §3 `replace` — `rebind_held_seat(seat, pane, op)` has no `replace` argument. If threads has already minted a bare seat on the restarted pane, the rebind has no defined outcome, even though §3 handles exactly this case for `resurrect_seat`.
- [suggested Should-fix] §4 "after an incarnation change"; Key decisions — The spec triggers the rebind on any "incarnation change" and does not separate a cold restart from a live handoff (`herdr update --handoff`), where agents survive. Graph would then rebind seats whose live agents are reattaching on their own, which collides with U2's unresolved question about "a binding that reconnects later".
- [suggested Should-fix] §4 op key `rebind:<clone>:<incarnation changed_at>`; §4.2 — A per-incarnation op key makes a definitive refusal final for the whole incarnation, and the spec does not separate permanent refusals from ones that are definitive but transient right after a restart (for example threads not yet seeing the new Herdr target), so a seat could stay held although a later retry would succeed.
- [suggested Should-fix] §4 op key `rebind:<clone>:<incarnation changed_at>` — A pending or unknown-outcome rebind from incarnation N has no rule for being cancelled or superseded when incarnation N+1 begins, and could replay against a stale pane.
- [suggested Should-fix] Key decisions (U2 open points); §4 op key — The design assumes U2 (the held-seat rebind) will be idempotent under retry, with a deduplicated op key and a defined answer when a lost response is retried. U2's design is not settled.
- [suggested Should-fix] §3 keyless Reversible row — The resurrect op key `resurrect:<clone>:<epoch>` assumes threads deduplicates by operation id across a graph crash between `resurrect_seat` succeeding and `SeatTransition::Acknowledge` being recorded. The retry behaviour is unspecified.
- [suggested Should-fix] §3; §4.5 — An undo whose resurrect fails has no status row or doctor finding. The only new degraded-state surface (§4.5 `clones.restart_held`) covers restart rebinds only.
- [suggested Should-fix] §3 table; Goal — The §3 undo table has no row for a keyed seat whose retirement is `Retired{Final}` (operator-finalized, or past its window), although the Goal promises undo restores the original seat for "adopted or created" tabs.
- [suggested Should-fix] Main challenges "The bump and the resurrect path must land together"; §5; beads hg-lnw.4/.6/.7 — The spec says the pin bump and the resurrect path "must land together", but the bead order puts the pin (hg-lnw.6, after hg-lnw.4) before the real adapter that registers v4 and implements `resurrect_seat` (hg-lnw.7). In between, a 3.6.0 pin with a v3 session cannot call `ResurrectSeat`, which is v4-only.
- [suggested Should-fix] Main challenges "A pin bump alone is not safe either" — The spec treats the reversible-keyless stall as a hazard that "a pin bump" would cause. Reversibility is decided by the daemon, though, and the herdr-threads installed on this host is already 3.5.0 while graph pins 3.1.0. So the `UnretireSeat`-on-keyless stall can occur now, before any of this work lands, and no bead covers that interim.
- [suggested Should-fix] Main challenges "`ResurrectSeat` answers `NotFound` for any seat that is not reversibly retired" — The spec states that `ResurrectSeat` answers `NotFound` for any seat that is not reversibly retired. The 3.5.0 code returns `TargetAlreadyOwned` first whenever the target pane is occupied, and returns `TargetUnresolved` for a finally retired seat reached by the operator path.
- [suggested Should-fix] §3 — The spec does not handle a keyless seat that another party resurrected or rebound between the close and the undo. Keyless seats are resurrectable by "any v4 session" (bead hg-lnw.7).
- [suggested Should-fix] Key decisions "U2 starts as an extension of `ResurrectSeat`, with the same authority"; §4.5 — For keyless seats the spec takes U2's authority to be "same authority" as `ResurrectSeat`, which does not fence keyless seats to their managing service, so the design assumes no other v4 session or operator action rebinds or resurrects the same seat between graph's fact read and its call.
- [suggested Should-fix] §3 "The agent then enrolls onto the original seat" — A ResurrectSeat on the reopened pane does not stop the agent's later enrolment on that pane from racing another seat claim. The spec relies on "the agent then enrolls onto the original seat" without saying what threads does if the pane gets a bare seat between the resurrect and the agent's check-in.

## Rejected (with reason)        ← so re-roasts don't re-litigate
- Key decisions (U2 open points); §4 table; §4.2 — The §4 table, refusal mapping, fake and tests assume particular answers to U2's still-open semantics; if ht-0f0r ships differently, rows such as shell and never-observed seats are refused and B2 is unmet.
  reason: rejected 3 to 0. The spec names U2's three open points and gives U2 its own design review. §1 gates the real adapter, the pin and the real-threads tiers on the 3.6.0 gate bead, and states the fallback: a different adapter, or the `restart_held` row (§4.5) with the gap reported as unmet B2. §4.2 and §4.5 define the refusal path.
- §4 "whose bound pane exists"; §4 table row "pane missing after restart" — The restart design assumes a pane keeps its id (and threads host identity) across a Herdr server restart; the spec never states or verifies it.
  reason: rejected 3 to 0. The premise is project baseline: CURRENT-DESIGN.md line 132 states "Herdr preserves pane ids across a restart, as it does tab and workspace ids", and docs/verification-matrix.md lines 190 and 272 record it as verified (spike 3). The renumbered case degrades to the unchanged "pane missing after restart" `resume_blocked` row. The "own held pane" question is a stated U2 open point.
- §4.2 "`NotFound` because the seat is already resolved on that pane counts as done" — §4.2 gives no way to tell that cause from others, and the inherited `ResurrectSeat` path would likely answer `TargetAlreadyOwned` for that case.
  reason: rejected 2 to 1. The ground seat confirmed at Nit, citing herdr-threads v3.5.0 src/store/seats/operator.rs: the `target_free` check returns `TargetAlreadyOwned` before the seat-state match. The reproduce seat verified the same code fact and still rejected, so the dissent is answered: U2 is unreleased and its error shape is a stated open point, the error mapping is an adapter detail behind the port method, and a misread case only leaves a spurious `rebind_refused` record because §4.2 proceeds with the relaunch on any refusal. Worth pinning the already-placed result when the U2 review lands.
- Key decisions "what happens to a binding that reconnects later"; §4 table — An old binding or cooperative reattach can contest the rebound seat after graph has launched a fresh agent on it.
  reason: rejected 3 to 0. "Cooperative continuity reattaches" appears only in the "Today" column; the "After" column replaces it with the rebind, and Key decisions says cooperative continuity is "no longer load-bearing for keyless seats". The late-reconnect question is a stated U2 open point owned by herdr-threads. The old agent process dies with the Herdr restart; a surviving stale binding is not shown.
- §3 `replace` paragraph — §3 does not say how graph learns the bare seat to pass as `replace`, or what happens when `None` is passed and a seat is minted on the reopened pane before `ResurrectSeat` runs.
  reason: rejected 3 to 0. §3 names the race and the contract (`replace` is the seat threads minted for the reopened pane, otherwise `None`). Which inspection returns the pane's seat is an adapter detail on the existing `SeatInspect` path. Validation of a stale `replace` belongs to threads; the effect is op-keyed and re-planned from a fresh fact. At most a unit test for the implementing bead.
- §2 "An older daemon refuses the v4 registration … (no silent fallback to v3)" — A daemon older than 3.6.0 takes down all of graph's threads integration; the spec states no upgrade ordering, rollback story or acceptance of that outage.
  reason: rejected 3 to 0. §2 states the daemon requirement (daemon >= T) and the no-fallback choice as a decision, and the failure is reported by the existing registration-failure path. §2 and §5 require a CHANGELOG migration note (daemon >= T, schema 19 one-way). A v3 fallback contradicts B3 and the one-service-session constraint. A possible one-sentence addition: "upgrade the daemon before graph".
