#### Important (Should Fix)

1. **Fence confirmed plans that carry old namespace intent.** `src/writer/mod.rs:292` fences only selected bookkeeping kinds; `src/threads/reconnect.rs:250` clears active participation but does not invalidate older stored plans. A concrete path is: create an unapplied `participation join <old-external-thread> --scope seat --seat <seat>` plan on node A; reconnect to B; then apply that original plan with its original hash. Admission deliberately leaves `relied_on` empty (`src/plan/commands.rs:204`, `src/plan/commands.rs:266`), and apply compares only recomputed effect sets (`src/plan/apply.rs:125`, `src/plan/apply.rs:148`). The join effect contains the thread string, scope and seat ID, with no namespace or revision (`src/plan/kinds_extra.rs:639`), so reconnect's revision bump does not change that effect. The plan therefore restores the old external thread string as active target-node participation, and current-epoch reconciliation can resolve a recipient and invite it there. This violates the requirement that old external references stay unresolved and never be automatically dispatched as target-node work. Bind namespace-sensitive confirmed plans to the epoch at planning time and reject crossing the boundary, or conservatively reject pre-boundary plans using their committed revision. Require a newly reviewed target-namespace plan. Add a real plan/writer regression for both an old stored plan applied later and an already-admitted plan queued behind reconnect; include analogous template/application plans that can introduce external thread IDs.

2. **Include the namespace epoch or intent-directory identity in the production service cache key.** `src/daemon/compose.rs:681` returns a cached `ServiceThreads` when `Discovered` matches, before calculating the current epoch journal path at `src/daemon/compose.rs:692`. `Discovered` contains only socket and node (`src/threads/adapter.rs:117`). Exact trigger: warm the service cache on A; reconnect A→B; publish B through `LazyMap`/the shared endpoint without a successful service-cache lookup on B; reconnect B→A at the original socket; then issue a correctly scoped current-epoch service call. The current marker/binding checks pass, but `cached == d` returns the old A client, whose journal is now retired. A mapping call can publish the binding independently at `src/daemon/compose.rs:849`, and reconnect can occur between that call and its following service call. The retirement check runs only during client construction (`src/threads/adapter.rs:169`); an existing client retains its journal and pending list. Its next mutation invokes `replay_pending`, can replay dormant old envelopes, writes new work to the retired journal, and may delete completed old envelopes (`src/threads/adapter.rs:270`, `src/threads/adapter.rs:293`). This is inside the production wrapper, so the disclosed limitation for independently held raw clients does not cover it. Compare endpoint plus epoch/journal path before cache reuse and construct a fresh client for each epoch. Add an A→B→A cache regression that intentionally leaves the A service cache untouched while B's binding is published and proves old intent bytes/pending work remain dormant.

3. **Complete epoch propagation across production callers and routing writebacks.** `src/threads/namespace.rs:128` treats absent task-local scope as the empty epoch, and `src/writer/mod.rs:297` rejects unscoped namespace bookkeeping after any reconnect. Several established production paths still operate without the new scope:

   - `src/daemon/compose.rs:389`: the connection probe calls `delivery_capability()` unscoped. Every post-reconnect probe is rejected before contacting the service, permanently reporting `components.threads.connected=false` even when scoped delivery works. Doctor then reports a failed threads check when the state directory exists (`src/daemon/doctor.rs:95`, `src/daemon/doctor.rs:112`). Give the probe an explicitly current epoch under the same quiescence contract; do not remove stale-call checking from reference-bearing calls.
   - `src/plan/reminders.rs:67`, `src/plan/reminders.rs:134`: rejection/failure reminders capture a current thread but no epoch, then notify unscoped. All initial and scheduled requester notices fail after reconnect, including operations created entirely on the new node. Capture the epoch from the same committed view as the destination, carry it in `Due`, scope the call, and salt its operation key. The daemon still installs this scheduler (`src/daemon/compose.rs:310`).
   - `src/transcripts/liveness.rs:56`, `src/transcripts/mod.rs:344`: `process_pending()` runs before the newly scoped liveness section. Its `request_delivery` writes at `src/transcripts/mod.rs:386` and `src/transcripts/mod.rs:404` therefore carry an empty epoch and are rejected even when they describe current-node requests. A pending request with no summarizer cannot record its undeliverable reason; the early failed commit also prevents subsequent routing work in that scan. `notify_undeliverable_once` remains unscoped, and both its service key and completion marker are unsalted (`src/transcripts/mod.rs:424`, `src/transcripts/mod.rs:435`). Capture the routing work's epoch with its snapshot, use it for writebacks and notification calls, and namespace the notification state.

   These are one incomplete API-contract migration, not reasons to weaken the fence. Add production-wrapper tests after reconnect covering healthy connection status, a newly rejected operation's requester reminder, and a pending request becoming undeliverable and later routable. Existing fake-port reconnect tests do not enforce the wrapper's task-local check; the real reconnect test explicitly scopes its direct calls and does not run these background paths (`tests/threads_real.rs:648`).
